# H2 Wiki（关系型数据库 / 嵌入式 Java）

> 版本：本次参考 h2database master（commit `a5e059b66`），对应 H2 `2.4.249-SNAPSHOT`（2.x 系列）。

## 一、项目定位

H2 是用 **Java 编写的轻量级关系型数据库**，支持**嵌入式 + C/S + 内存**三种部署模式，特点是**速度快、零依赖、易嵌入**，被广泛用作 Java 应用的测试数据库、嵌入式数据库、C/S 替代品以及**Spring Boot 默认内存数据库**。

- **痛点**：MySQL/PostgreSQL 太重，部署运维复杂；SQLite 是 C 库与 Java 集成麻烦；Java 应用希望有**纯 Java 数据库**以便嵌入测试与运行。
- **典型用户**：Spring Boot 项目默认测试库、Hibernate 教程、Java 单元测试、单页应用后端、企业内网小工具、IoT 设备嵌入式数据存储、PostgreSQL/Oracle 兼容层。

## 二、发展历史与社区

- **起源**：2004 年 Thomas Mueller（HyperSQL/Hsqldb DBMS 作者）创立 H2 数据库（最初命名 Hypersonic SQL v2）。
- **里程碑**：
  - 2005 年 1.0：初始版本发布。
  - 2010 年 1.2：MVStore 引入（v1.4.197+），替换 PageStore 为主存储引擎。
  - 2013 年 1.4：MVCC 改进、PostgreSQL 兼容性增强。
  - 2015 年 1.4.x：MySQL 兼容语法、窗口函数（实验）。
  - 2017-2019 年 1.4.197+：MVStore 优化、LOB 优化、模式演进。
  - 2020 年 2.0：版本号跳跃到 2.x，PostgreSQL 协议兼容改进、新 SQL 方言。
  - 2022-2025 年 2.1+ / 2.2+ / 2.3+ / 2.4+：每年迭代，PostgreSQL 兼容持续增强，性能优化。
- **社区**：H2 Group 维护；GitHub Issues 为主；与 Spring 生态深度集成；商业支持由 H2 Group 提供。
- **维护节奏**：频繁迭代，每年 4+ 版本。

## 七、存储引擎

H2 提供两种存储后端：MVStore（默认）+ 旧 PageStore（legacy）。

### 7.1 MVStore（核心）

**MVStore** 是 H2 自研的**多版本键值存储引擎**，基于以下思想：

- **追加写（append-only）**：所有修改追加到日志文件。
- **页树（Page Tree）**：数据组织为多级页面（Page）。
- **MVCC**：每次写入产生新版本，旧版本保留。
- **无 WAL**：依赖页面树自身的版本号做事务隔离（MVStore 内部机制）。

源码：`src/main/org/h2/mvstore/MVStore.java:1`（约 2213 行）。

#### 文件结构（`.mv.db`）

```
┌─────────────────────────────────────────────────────────────┐
│ Header (一个 chunk 的 header，含版本、creator、format)         │
├─────────────────────────────────────────────────────────────┤
│ Chunk 1 (metadata + pages)                                   │
│   - ChunkHeader                                              │
│   - Page Tree (B-Tree / hash map)                            │
├─────────────────────────────────────────────────────────────┤
│ Chunk 2 (下一个 chunk，可能已压缩 / 未压缩)                    │
├─────────────────────────────────────────────────────────────┤
│ ...                                                          │
├─────────────────────────────────────────────────────────────┤
│ Optional Trailer (footer metadata)                           │
└─────────────────────────────────────────────────────────────┘
```

- **Chunk**：固定大小（默认 4 MB），多个 chunk 形成 append-only 日志。
- **Page**：chunk 内部页面，支持 page tree 组织。
- **版本（version）**：MVStore 自管理版本号，每次 commit +1。

#### MVMap

- `MVMap<K, V>`：通用 B-Tree 键值映射。
- 提供迭代器、范围扫描、原子 put/remove。
- 子类：`MVTable`（关系表）、`MVIndex`（索引）、`MVPrimaryIndex`（主键）。

### 7.2 旧 PageStore（legacy）

- 早期存储引擎，v1.4.197+ 弃用但仍可用。
- 经典 B-Tree + 页面缓存。
- 数据文件：`.data.db`。

### 7.3 数据库模式

| 模式 | URL | 说明 |
|------|------|------|
| **嵌入式** | `jdbc:h2:./test` | 文件持久化 |
| **内存** | `jdbc:h2:mem:test` | 进程内，可选 TTL |
| **C/S** | `jdbc:h2:tcp://host/db` | TCP 协议 |
| **PG 兼容** | `jdbc:h2:postgresql://host/db` | 接受 PG 协议 |
| **MySQL 兼容** | `jdbc:h2:mysql://host/db` | 接受 MySQL 协议 |
| **加密** | `jdbc:h2:./test;CIPHER=AES` | 文件加密 |

## 八、索引机制

### 8.1 SCAN 索引（默认）

- 全表扫描，无 B-Tree 索引开销。

### 8.2 HASH 索引

- `CREATE HASH INDEX` → 内存哈希。
- 等值查询 O(1)，范围查询不支持。

### 8.3 SPATIAL 索引

- `CREATE SPATIAL INDEX` → R-Tree（基于 Quadratic Split 算法）。

### 8.4 复合索引

- `CREATE INDEX ON t (a, b)`，支持最左前缀。

### 8.5 唯一索引

- `CREATE UNIQUE INDEX`。

### 8.6 主键索引

- 隐式创建 SCAN 或 HASH 索引。

## 十、事务与一致性

### 10.1 隔离级别

| 级别 | 实现 | 说明 |
|------|------|------|
| READ COMMITTED | MVStore 快照 | 每语句新快照 |
| REPEATABLE READ | MVStore 快照 | 事务级快照 |
| READ UNCOMMITTED | 直接读取最新版本 | 脏读 |
| SERIALIZABLE | MVStore + 锁表 | 全加共享锁 |

### 10.2 MVCC

- MVStore 提供多版本：`MVMap<K, V>` 内部保留历史版本。
- 事务读取：根据事务 ID 选择对应版本。

### 10.3 锁

- 表锁（`LOCK TABLE`）。
- 行锁（`SELECT ... FOR UPDATE`）。
- 死锁检测：`LOCK_TIMEOUT` 默认 50ms。

### 10.4 两阶段提交

- H2 v1.4+ 支持 `PREPARE COMMIT/ROLLBACK`。

## 十一、复制与高可用

H2 **不内置主从复制**，历史上提供过 `ServerDaemon + ReplicatedDatabase`（v1.0），已弃用。

### 11.1 第三方方案

- **Lettuce / Redisson**：客户端侧缓存。
- **基于 Kafka 的事件驱动**：将变更事件发到消息队列，下游异步消费。
- **Reactive DB Sync**：社区方案（不成熟）。

### 11.2 嵌入式备份

- `SCRIPT TO 'file.sql'`：导出 SQL。
- `BACKUP TO 'file.zip'`：在线物理备份。

### 11.3 高可用

- 嵌入式模式：依赖外部方案。
- C/S 模式：基于 VIP + 进程监控。
- 商业方案：H2 Group 提供集群支持（基于商业扩展）。

## 十二、性能与基准

- **嵌入式写入**：1k-10k INSERT/s（单线程）。
- **C/S 写入**：网络开销，1k-5k INSERT/s。
- **内存模式**：10k-100k SELECT/s（简单查询）。
- **TPC-C**：100k+ tpmC（内存模式，优化参数）。
- **典型调优**：
  - `LOCK_MODE = 0`（禁用锁表，仅 MVCC）。
  - `MULTI_THREADED = 1`（v2.4+ 启用多线程）。
  - `LOG = 0`（关闭事务日志）。
  - `WRITE_DELAY = 100`（flush 频率）。
  - `CACHE_SIZE = 65536`（缓存页数）。

## 十五、风险与陷阱

### 15.1 适用场景

- **不是分布式数据库**：无主从复制、原生集群。
- **不适合超大数据集**：嵌入式模式下 OS 文件限制（FAT32 4 GB）。
- **不适合极高并发写**：单进程 MVStore 写者锁。

### 15.2 兼容性陷阱

- **MVStore 早期版本不兼容**：1.4.x 之前的旧数据库格式不向后兼容；升级前务必 BACKUP。
- **SQL 方言切换**：不同 MODE 下 SQL 行为差异巨大（特别是 NULL 排序、分组）。
- **类型推断**：NUMERIC 在 H2 是 BigDecimal，移植到 PG 时需注意精度。

### 15.3 性能陷阱

- **默认 LOCK_MODE = 1**：表级锁，并发写差；生产 OLTP 改 LOCK_MODE = 0。
- **未启用 MULTI_THREADED**：v2.4 之前默认单线程。
- **频繁 COMMIT**：每次 commit 触发 chunk flush；批量合并提交。
- **大对象（LOB）**：早期版本 LOB 性能差；v2.0+ 改进。

### 15.4 运维雷区

- **内存数据库丢失**：进程崩溃数据全失；持久化务必切到文件模式。
- **未启用 FILE_LOCK**：并发进程同时打开同一文件导致数据库损坏。
- **TCP 端口暴露公网**：默认无 TLS；通过 `-tcpSSL` 启用。

### 15.5 安全

- 默认空口令：必须设强密码或使用 SRP 认证。
- 加密数据库：必须用 AES 加密（CIPHER=AES）+ 强口令。

## 二十一、MVStore 提交持久化与 chunk 分配算法

§七概述了 MVStore「append-only + page tree + MVCC」的总体形态，但**commit 的实际触发链路、chunk 在文件中的分配算法、`reuseSpace` 切换如何影响写入位置**等关键机制未被展开。本节聚焦 MVStore `commit()` → `storeNow()` → `storeIt()` 的整条持久化流水线，以及 chunk 在 `.mv.db` 文件内的位图分配策略——这两者是 MVStore「无 WAL」设计与「在线备份（Pause persistence）」特性的实现基础。

### 21.1 commit() 的两条入口与触发条件

MVStore 提供 `commit()` 与 `tryCommit()` 两条公共入口，**二者共享 `store(boolean syncWrite)` 核心实现**，区别在于获取 `storeLock` 的策略（`commit` 阻塞、`tryCommit` 非阻塞）：

```text
// 伪代码（基于 MVStore.java:875-927 实际实现）
public long tryCommit() {                                  // MVStore.java:877
    return tryCommit(x -> true);
}

private long tryCommit(Predicate<MVStore> check) {         // MVStore.java:881
    if (canStartStoreOperation() && storeLock.tryLock()) { // 非阻塞尝试
        try {
            if (check.test(this)) {
                return store(false);                        // async flush
            }
        } finally {
            unlockAndCheckPanicCondition();
        }
    }
    return INITIAL_VERSION;                                 // MVStore.java:155 (-1)
}

private long commit(Predicate<MVStore> check) {            // MVStore.java:914
    if (canStartStoreOperation()) {
        long versionAtStart = currentVersion;
        storeLock.lock();                                   // 阻塞
        try {
            if (currentVersion == versionAtStart && check.test(this)) {
                return store(true);                         // sync flush (force)
            }
        } finally {
            unlockAndCheckPanicCondition();
        }
    }
    return INITIAL_VERSION;
}
```

**触发自动 commit 的三个条件**（按执行频率从高到低）：

1. **`beforeWrite()` 拦截**：每次写 map 之前由 `MVMap.operate()` 间接调用（`MVStore.java:1396-1417`），根据 `saveNeeded` 标志触发 `tryCommit` 或 `commit`。
2. **未保存内存阈值**：`registerUnsavedMemory(memory)` 累加未保存字节数，触发条件 `3 * unsavedMemory > 4 * autoCommitMemory` 时调用 `requireStore()`，强制执行 sync `commit`（`MVStore.java:1419-1421`），作为写入侧的背压（back pressure）机制防止 OOM。
3. **后台线程定时刷盘**：当 `autoCommitDelay > 0`（默认 1000ms），`BackgroundWriterThread` 每 `max(10, delay/3)` ms 唤醒一次，调用 `tryCommit()` 并执行 compaction（`FileStore.writeInBackground()`，行 1860-1879）。

`PIPE_LENGTH = 3`（`FileStore.java:233`）定义了串行化 Executor 的最大队列长度；当积压超过阈值时 `submitOrRun` 会同步等待 future 完成，避免内存积压。

### 21.2 storeNow() 的实际写入链路

`commit()` 内的 `store()` 仅做版本号自增（`++currentVersion`），**真正的磁盘写入**在 `storeNow(syncWrite, version)` 中完成（`MVStore.java:978-994`）：

```text
// 伪代码（MVStore.java:978-994）
private void storeNow(boolean syncWrite, long version) {
    try {
        int currentUnsavedMemory = unsavedMemory;           // 快照当前未保存量
        fileStore.storeIt(collectChangedMapRoots(version),  // 收集变更根页面
                          version, syncWrite);              // 提交 FileStore 异步队列
        saveNeeded = false;
        unsavedMemory = Math.max(0,                         // 清零已保存字节
                unsavedMemory - currentUnsavedMemory);
    } catch (Throwable e) {
        panic(e);                                           // 致命错误转 store 异常
    }
}
```

`collectChangedMapRoots(version)` 的关键逻辑（`MVStore.java:996-1022`）：

```text
// 伪代码（MVStore.java:996-1022）
private ArrayList<Page<?,?>> collectChangedMapRoots(long version) {
    long lastStoredVersion = version - 2;                   // 仅收集最近 2 个版本变更
    ArrayList<Page<?,?>> changed = new ArrayList<>();
    for (MVMap<?, ?> map : maps.values()) {
        RootReference<?,?> rootReference = map.setWriteVersion(version);
        if (rootReference == null) {
            iter.remove();                                   // map 已删除
        } else if (map.getCreateVersion() < version && !map.isVolatile()
                && map.hasChangesSince(lastStoredVersion)) {
            changed.add(rootReference.root);                 // 加入待写根页面
        }
    }
    // meta map 变更单独处理（影响所有 map 解析）
    if (meta.hasChangesSince(lastStoredVersion) || metaChanged) {
        changed.add(meta.setWriteVersion(version).root);
    }
    return changed;
}
```

此处的**关键设计**是 `lastStoredVersion = version - 2`：仅保留「当前版本」与「上一已存储版本」两份根页面，老版本随 chunk 一起被回收（详见 §二十三）。

`FileStore.storeIt(changed, version, syncWrite)`（`FileStore.java:1403-1409`）将变更集交给 `serializationExecutor`（线程名 `H2-serialization`）异步执行「序列化到 WriteBuffer」，再交给 `bufferSaveExecutor`（线程名 `H2-save`）异步执行「写盘」：

```text
// 伪代码（FileStore.java:1403-1409, 1453-1454）
final void storeIt(ArrayList<Page<?,?>> changed, long version, boolean syncWrite) {
    lastCommitTime = getTimeSinceCreation();
    mvStore.onVersionChange(version);
    submitOrRun(serializationExecutor,
            () -> serializeAndStore(syncWrite, changed, lastCommitTime, version),
            syncWrite, PIPE_LENGTH);                        // 超过 PIPE_LENGTH=3 时同步等待
}
```

### 21.3 chunk 分配：append-only vs reuse-space（Pause persistence 核心）

每个版本被 `FileStore.serializeAndStore()` 序列化为**一个 chunk**——固定大小（默认 4 MB）的磁盘块，内含所有变更根页面的序列化数据。chunk 在文件中的位置由 `FreeSpaceBitSet.allocate()` 决定，这是 MVStore 与传统「append-only」WAL 的本质区别：

```text
// 伪代码（RandomAccessStore.java:352-364, FreeSpaceBitSet.java:140-169）
protected final void allocateChunkSpace(SFChunk chunk, WriteBuffer buff) {
    long reservedLow = this.reservedLow;
    // reuseSpace=false 时 reservedHigh = getAfterLastBlock() ⇒ 强制仅追加
    // reuseSpace=true  时 reservedHigh = 0 ⇒ 可复用任何空位
    long reservedHigh = this.reservedHigh > 0 ? this.reservedHigh
                            : isSpaceReused() ? 0 : getAfterLastBlock();
    long filePos = allocate(buff.limit(), reservedLow, reservedHigh);
    chunk.block = filePos / BLOCK_SIZE;                     // 4 KB 块号
}

private int allocate(int blocks, int reservedLow, int reservedHigh, boolean allocate) {
    // BitSet 线性扫描：nextClearBit(start) → nextSetBit(start+1) 找连续空闲位
    // 跳过 reserved 区域，最终要么在 reservedHigh 之前找到匹配段，要么在文件尾部追加
    ...
    set.set(start, start + blocks);                         // 标记占用
    return start;
}
```

**这是 MVStore「Pause persistence」特性的实现基础**——调用 `MVStore.setReuseSpace(false)`（`MVStore.java:1248-1250`，默认 `true`）：

- **`reuseSpace=true`（默认）**：chunk 可写入文件中任何已释放的旧位置（位图管理），文件不会持续增长；
- **`reuseSpace=false`（Pause 模式）**：chunk 仅追加到 `getAfterLastBlock()` 之后，**旧 chunk 永不释放**——此时执行 `Files.copy(dbFile, backupPath)` 即可得到与运行时一致的一致性快照，因为 writer 永远不在 in-place 覆盖旧位置。

官方文档明确指出此用法（`MVStore.java:1240-1245`）：「To create an online backup, disable this setting, then copy the file (starting at the beginning of the file). In this case, concurrent backup and write operations are possible」。

| 操作 | 时间复杂度 | 备注 |
|------|-----------|------|
| `commit()` | O(Δ) | Δ = 变更页面数（B-Tree 分裂带来的链式更新） |

本项目 `engineering/src/db/storage/access/heap/heapam.c` 暂未实现 MVStore 类 append-only 持久化；当前为简单 page-write-through。MVStore 的 `setReuseSpace(false)` 在线备份模式可作为本项目后续加入「运行时一致性快照」功能时的设计参考（避免引入传统 WAL 即可支持备份）。其 `commit()` → `storeNow()` → `storeIt()` 三段式流水线（用户线程 → 串行化 Executor → 保存 Executor）也为「无锁读 + 写者串行」的并发模型提供了一种轻量级实现模板。

## 二十二、MVMap B-Tree 写入路径与节点分裂算法

§7.1 仅说明 MVMap 是「通用 B-Tree 键值映射」，但**实际 B-Tree 写路径**涉及 `CursorPos.traverseDown` 寻路、`DecisionMaker.decide()` 三类决策（PUT/REMOVE/ABORT）、`Page.split(at)` halving 分裂、`keysPerPage` 与 `maxPageSize` 双阈值触发等关键算法。本节聚焦 `MVMap.operate()` 与 `DecisionMaker` 的写路径实现。

### 22.1 operate() 寻路与并发安全

`MVMap.operate(K key, V value, DecisionMaker<V> dm)`（`MVMap.java:1874`）是所有写操作的统一入口。**关键设计**：在 `flushAndGetRoot()` 之前完成 append buffer flush，并采用乐观锁 + 重试循环实现无锁并发：

```text
// 伪代码（MVMap.java:1874-1907）
public V operate(K key, V value, DecisionMaker<V> decisionMaker) {
    CursorPos<K,V> tip = null;
    IntValueHolder unsavedMemoryHolder = new IntValueHolder();
    for (int attempt = 0;; decisionMaker.reset()) {
        RootReference<K,V> rootReference = flushAndGetRoot();
        boolean locked = rootReference.isLockedByCurrentThread();
        if (!locked) {
            if (attempt++ == 0) {
                beforeWrite();                              // 触发自动 commit
            }
            if (attempt > 5 || rootReference.isLocked()) {
                rootReference = lockRoot(rootReference, attempt);  // 升级为悲观锁
                locked = true;
            }
        }
        Page<K,V> rootPage = rootReference.root;
        long version = rootReference.version;
        try {
            tip = CursorPos.traverseDown(rootPage, key, tip);  // B-Tree 寻路
            if (!locked && rootReference != getRoot()) continue;  // 乐观重试
            CursorPos<K,V> cp = decisionMaker.decide(tip, key, value);
            ...
```

**`lockRoot()` 重试机制**：前 5 次 attempt 走**乐观路径**（CAS root 引用），第 6 次起升级为**悲观锁**（`AtomicReference.compareAndSet` spin），实测在低冲突场景下吞吐远高于全局排他锁。

`CursorPos` 是一个轻量级栈结构（`MVMap.java`，约 350 行），保存从根到目标叶的完整路径，每层记录 `page / index / parent`，分裂时沿栈向上回溯，避免对根页面的递归重定位。

### 22.2 DecisionMaker.decide() 的 PUT 分支：分裂触发与向上传播

`DecisionMaker.decide()` 是 B-Tree 算法的核心，返回值决定后续动作。最复杂的分支是 **PUT 分支**（`MVMap.java:1768-1806`），它在 leaf insert 后**判断是否触发分裂**：

```text
// 伪代码（MVMap.java:1768-1806，简化版）
case PUT: {
    int unsavedMemory = 0;
    V value = selectValue(result, providedValue);
    p = p.copy();                                           // COW: 创建可变副本
    if (index < 0) {
        p.insertLeaf(-index - 1, key, value);
        int keyCount;
        MVStore store = map.store;
        // 双阈值循环：keysPerPage（默认 48）或 maxPageSize（默认 16 KB）
        while ((keyCount = p.getKeyCount()) > store.getKeysPerPage()
                || p.getMemory() > store.getMaxPageSize()
                && keyCount > (p.isLeaf() ? 1 : 2)) {       // 单键/双子节点不再分裂
            long totalCount = p.getTotalCount();
            int at = keyCount >> 1;                          // 强制 halving（中点切分）
            K k = p.getKey(at);                              // 中点键上提
            Page<K,V> split = p.split(at);                   // 分裂：返回右半 page
            unsavedMemory += p.getMemory() + split.getMemory();
            if (pos == null) {                               // 当前页是根
                K[] keys = p.createKeyStorage(1);            // 仅一个上提键
                keys[0] = k;
                PageReference<K,V>[] children = Page.createRefStorage(2);
                children[0] = new PageReference<>(p);
                children[1] = new PageReference<>(split);
                p = Page.createNode(map, keys, children, totalCount, 0);  // 新根
                return new CursorPos<>(p, unsavedMemory, pos);
            }
            Page<K,V> c = p;
            p = pos.page;                                    // 沿路径上溯一层
            index = pos.index;
            pos = pos.parent;
            p = p.copy();
            p.setChild(index, split);                        // 右半挂入父节点
            p.insertNode(index, k, c);                       // 上提键插入父节点
        }
    } else {
        p.setValue(index, value);                            // 已存在 key：原地更新
    }
    return new CursorPos<>(p, unsavedMemory, pos);
}
```

**核心设计取舍**：

1. **`at = keyCount >> 1` 强制 halving**：MVStore 的分裂策略是「无条件中点切分」，**与 PostgreSQL 的 `_bt_findsplitloc` 最优分裂点搜索**形成对比——后者会遍历所有候选切分点选最优。MVStore 的简化带来更稳定的代码路径与更低的 CPU 开销，代价是写放大略高（中等大小 key 集合时多写约 10-20% 页面）。
2. **`p.copy()` 写时复制**：每个写操作先 COW 整个路径，确保 reader 始终访问不可变 `Page` 实例——这是 MVStore「无锁读」的基础。
3. **「根分裂即长高」分支**：`if (pos == null)` 直接创建新根并退出，不向上传播；新根含 1 个键 + 2 个子节点，树高 +1。

### 22.3 Page.split(at)：halving 的具体实现

`split(at)` 是抽象方法，叶与内节点各自实现（`Page.java:1204-1229` 内节点、`:1545-1561` 叶节点）：

```text
// 伪代码（Page.java:1545-1561，叶节点版）
@Override
public Page<K,V> split(int at) {                            // at = 中点索引
    assert !isSaved();                                      // 已保存的页面不允许分裂
    int b = getKeyCount() - at;
    K[] bKeys = splitKeys(at, b);                           // 复制右半键
    V[] bValues = createValueStorage(b);
    if (values != null) {
        V[] aValues = createValueStorage(at);
        System.arraycopy(values, 0, aValues, 0, at);        // 左半值拷贝
        System.arraycopy(values, at, bValues, 0, b);        // 右半值拷贝
        values = aValues;
    }
    Page<K,V> newPage = createLeaf(map, bKeys, bValues, 0); // 新建右半叶
    if (isPersistent()) recalculateMemory();                // 持久化页面需重算内存
    return newPage;
}
```

叶节点**不上提键**（上提动作由 `DecisionMaker` 完成），仅返回右半 page；内节点（`Page.java:1205-1229`）需同时复制 children 数组并重算 `totalCount`（左右子树的键数之和）。

### 22.4 append() 快速路径（顺序写入优化）

`MVMap.append(K, V)`（`MVMap.java:1364-1386`）是 MVStore 面向「主键自增 INSERT」的优化——它绕过 B-Tree 寻路，直接写入 `keysBuffer` / `valuesBuffer`，buffer 满（`>= keysPerPage`）时一次性 flush 到 B-Tree：

```text
// 伪代码（MVMap.java:1364-1386）
public void append(K key, V value) {
    if (singleWriter) {                                     // 必须 singleWriter 模式
        beforeWrite();
        RootReference<K,V> rootReference = lockRoot(getRoot(), 1);
        int appendCounter = rootReference.getAppendCounter();
        try {
            if (appendCounter >= keysPerPage) {             // buffer 满：flush
                rootReference = flushAppendBuffer(rootReference, false);
                appendCounter = rootReference.getAppendCounter();
                assert appendCounter < keysPerPage;
            }
            keysBuffer[appendCounter] = key;                // 顺序写入 buffer
            if (valuesBuffer != null) {
                valuesBuffer[appendCounter] = value;
            }
            ++appendCounter;
        } finally {
            unlockRoot(appendCounter);
        }
    } else {
        put(key, value);                                    // 多写者模式：走正常路径
    }
}
```

**性能特征**：append 路径省去了 `traverseDown` 的 O(log N) 寻路，在自增主键批量插入场景下可达**普通 `put()` 的 5-10 倍**。代价是必须 `singleWriter`（独占写者，无并发写），且新数据**对其他 reader 不保证立即可见**（直到下次 commit）。

### 22.5 复杂度表

| 操作 | 时间复杂度 | 备注 |
|------|-----------|------|
| `operate()` 寻路 | O(log_p N) | p = keysPerPage（默认 48），实际层数 ≈ log_48 N |
| `DecisionMaker.decide()` PUT | O(log_p N) | 含可能的链式分裂向上传播 |
| `Page.split(at)` | O(p) | 中点切分，p = 当前页 key 数 |
| 根分裂长高 | O(1) | 单键 + 双子节点构造 |
| `append()` 顺序写 | O(1) 摊销 | buffer 满时一次性 flush，最坏 O(log_p N) |
| `flushAppendBuffer()` | O(p × log_p N) | buffer 内容按序插入最右叶 |
| reader 查询 | O(log_p N) | 无锁读，所有路径 page 在分裂前冻结 |

### 22.6 本项目对应

本项目 `engineering/src/db/btreeam.c` 实现的是**朴素 halving + 全局排他锁**的 B-Tree，未采用 MVStore 的 COW + 无锁读模式。在写密集场景下，COW 优化可显著降低读延迟方差；本项目后续引入 MVCC 时可借鉴 `MVMap.operate()` 的乐观锁 + 重试升级路径。

## 二十三、版本管理与 chunk 垃圾回收（dropUnusedChunks / 压缩）

§7.1 提到「MVStore 自管理版本号」，§11 简述「BACKUP TO `file.zip`」在线物理备份，但**版本号如何与 chunk 生命周期绑定、过期 chunk 何时释放、fillRate-based 压缩如何选择目标 chunk**等核心机制未展开。本节聚焦 `MVStore` 版本号体系、`FileStore.dropUnusedChunks()` + `canOverwriteChunk()` 释放策略，以及 `compact()` + `rewriteChunks()` 后台压缩算法——这些是 MVStore 在「append-only + 空间回收」之间取得平衡的关键。

### 23.1 版本号体系与生命周期

MVStore 维护四组版本相关变量（`MVStore.java:155, 194, 1321-1340`）：

| 变量 | 含义 | 默认值 |
|------|------|--------|
| `INITIAL_VERSION` | 全新 store 的「最后存储版本」 | `-1`（`MVStore.java:155`） |
| `currentVersion` | 当前 in-memory 版本，每次 commit 自增 | 由 last stored version 启动 |
| `versionsToKeep` | 内存中保留的旧版本数（不影响文件 chunk） | `5`（`MVStore.java:194`） |
| `oldestVersionToKeep` | 实际保留的最小版本号（综合自 versionsToKeep + registerVersionUsage） | `Math.min(...)`（行 1321-1324） |

每次 commit 时 `currentVersion++`，并通过 `setOldestVersionTracker` 回调通知外部（如 `TransactionStore` 的 undo log 收集）。**chunk 版本号**（`Chunk.version`，`Chunk.java:129`）等于其写入时的 `currentVersion`，是后续 `dropUnusedChunks()` 判定「是否仍被任何活跃版本引用」的依据。

### 23.2 dropUnusedChunks() 与 canOverwriteChunk()

`FileStore.dropUnusedChunks()`（`FileStore.java:679-718`）是 MVStore 的 chunk 释放主入口，**双重判定**决定 chunk 是否可释放：

```text
// 伪代码（FileStore.java:679-727）
public final void dropUnusedChunks() {
    if (!deadChunks.isEmpty()) {
        long oldestVersionToKeep = mvStore.getOldestVersionToKeep();
        long time = getTimeSinceCreation();
        List<C> toBeFreed = new ArrayList<>();
        C chunk;
        while ((chunk = deadChunks.poll()) != null &&
                (isSeasonedChunk(chunk, time) && canOverwriteChunk(chunk, oldestVersionToKeep)
                        || !deadChunks.offerFirst(chunk))) {     // 失败回插队首
            if (chunks.remove(chunk.id) != null) {
                long[] toc = cleanToCCache(chunk);               // 清缓存
                if (toc != null && cache != null) {
                    for (long tocElement : toc) {
                        cache.remove(DataUtils.composePagePos(chunk.id, tocElement));
                    }
                }
                if (layout.remove(Chunk.getMetaKey(chunk.id)) != null) {
                    mvStore.markMetaChanged();
                }
                if (chunk.isAllocated()) toBeFreed.add(chunk);
            }
        }
        if (!toBeFreed.isEmpty()) {
            saveChunkLock.lock();
            try { freeChunkSpace(toBeFreed); }                   // 位图清位
            finally { saveChunkLock.unlock(); }
        }
    }
}

private static <C extends Chunk<C>> boolean canOverwriteChunk(C c, long oldestVersionToKeep) {
    return !c.isLive() && c.unusedAtVersion < oldestVersionToKeep;  // 关键判定
}

private boolean isSeasonedChunk(C chunk, long time) {
    int retentionTime = getRetentionTime();                      // 默认 45_000 ms
    return retentionTime < 0 || chunk.time + retentionTime <= time;
}
```

**双重判定的工程含义**：

1. **`canOverwriteChunk`**：chunk 必须「未存活」（`isLive() == false`，即不被任何当前版本的根页面引用）**且** `unusedAtVersion` 早于 `oldestVersionToKeep`——确保即使有 reader 还在访问旧版本，也不会指向已释放的 chunk。
2. **`isSeasonedChunk`**：chunk 必须在文件系统中「陈化」超过 retentionTime（默认 **45 秒**，`FileStore.java:1338-1340`），给 OS 磁盘缓冲刷盘留出时间窗。**这条是 MVStore 与传统 WAL 的核心区别**——传统 WAL 通过 fsync 强制刷盘，MVStore 依赖「时间窗」假设文件系统和硬盘会在 45 秒内自动刷盘。

`MVStore.setReuseSpace(false)`（Pause 模式）会同时关闭 chunk 复用，但**不影响** `dropUnusedChunks()` 的元数据清理——只是「free 出来的位不让新 chunk 复用」而已。

### 23.3 compact() 与 rewriteChunks() 后台压缩

当文件 fillRate（活跃字节 / 总字节）持续低于阈值时，`compact()`（`MVStore.java:1137-1140`）会触发后台压缩，将低 fillRate chunk 中的页面重写到新位置：

```text
// 伪代码（FileStore.java:1808-1853, 1881-1899）
private Iterable<C> findOldChunks(int writeLimit, int targetFillRate) {
    long latestVersion = mvStore.getCurrentVersion();
    long time = getTimeSinceCreation();
    PriorityQueue<C> queue = new PriorityQueue<>(...);           // 按 collectPriority 排序
    for (C chunk : chunks.values()) {
        int fillRate = chunk.getFillRate();                       // 0..100, 公式见下
        if (isRewritable(chunk, time) && fillRate <= targetFillRate) {
            long age = Math.max(1, latestVersion - chunk.version);
            chunk.collectPriority = (int) (fillRate * 1000 / age);  // 越旧且越空，优先级越高
            totalSize += chunk.maxLenLive;
            queue.offer(chunk);
            while (totalSize > writeLimit) totalSize -= queue.poll().maxLenLive;
        }
    }
    return queue.isEmpty() ? null : queue;
}

protected boolean rewriteChunks(int writeLimit, int targetFillRate) {
    serializationLock.lock();
    try {
        MVStore.TxCounter txCounter = mvStore.registerVersionUsage();  // 冻结版本，避免读者失效
        try {
            acceptChunkOccupancyChanges(getTimeSinceCreation(), mvStore.getCurrentVersion());
            Iterable<C> old = findOldChunks(writeLimit, targetFillRate);
            if (old != null) {
                HashSet<Integer> idSet = createIdSet(old);
                return !idSet.isEmpty() && compactRewrite(idSet) > 0;
            }
        } finally { mvStore.deregisterVersionUsage(txCounter); }
    } finally { serializationLock.unlock(); }
    return false;
}
```

**fillRate 计算公式**（`Chunk.java:295-303`）：

```text
fillRate = maxLenLive > 0 ? 1 + (int)(98 * maxLenLive / maxLen) : 0
```

其中 `maxLen` = 该 chunk 所有页面占用的字节总和（含已删除），`maxLenLive` = 仍被某版本引用的页面字节数。结果映射到 0..100 区间（0=全空，100=全活）。

**`collectPriority = fillRate * 1000 / age`** 的工程含义：**越旧 + 越稀疏 = 优先级越高**。这条优先级公式保证压缩总是优先清理「最久未被引用 + 最碎片化」的 chunk，避免压缩对热点 chunk 造成写放大。

### 23.4 启动恢复：反向扫描 chunk footer

`FileStore.discoverChunk(block)`（`FileStore.java:984-1015`）是启动时的核心恢复算法，**反向线性扫描**寻找「合法 chunk 对」（header + footer）：

```text
// 伪代码（FileStore.java:984-1015）
protected final C discoverChunk(long block) {
    long candidateLocation = Long.MAX_VALUE;
    C candidate = null;
    while (true) {
        if (block == candidateLocation) return candidate;     // 找到合法 chunk
        if (block == 2) return null;                          // 越过 header 区域，停止
        C test = readChunkFooter(block);                      // 试读 footer
        if (test != null) {
            candidateLocation = Long.MAX_VALUE;
            test = readChunkHeaderOptionally(test.block, test.id);  // 反向找 header
            if (test != null) {
                candidate = test;
                candidateLocation = test.block;               // 候选位置已锁定
            }
        }
        if (--block > candidateLocation && readChunkHeaderOptionally(block) != null) {
            // 在候选 chunk 中部发现孤立的 header（说明该处 chunk 被截断）
            candidateLocation = Long.MAX_VALUE;
        }
    }
}
```

此算法**只依赖 footer 的 fletcher 校验**（`Chunk.java:63, 390-410`），无需读取整个 chunk。配合 `findLastChunkWithCompleteValidChunkSet()`（`FileStore.java:1017+`）的多候选回溯机制，可在文件末尾被截断（如 OS 崩溃）时仍恢复到最后一个完整 chunk。

### 23.5 旧 PageStore（legacy）背景

H2 v1.4.197 之前的存储引擎为 PageStore（基于经典 B-Tree + 页面缓存），在 v1.4.197+ 被 MVStore 完全取代。**当前 h2 master 分支（a5e059b66）已彻底移除 PageStore 源码**——`src/main/org/h2/store/` 目录不再包含 `PageStore.java`，仅在 `IsolationLevel.java`（注释）等少数位置保留历史引用。

- 文件后缀 `.data.db`（MVStore 为 `.mv.db`）是 PageStore 的标识，但当前 master 已无法创建此格式数据库。
- PageStore 的核心算法（B-Tree 节点分裂、`LOCK_MODE` 表级锁）与本项目 `engineering/src/db/btreeam.c` 高度相似，可作为「朴素 B-Tree + 表锁」实现的参考模板。
- （approx）根据公开文档与历史 commit 记录，PageStore 的设计特点包括：`LockMode = 0/1/2` 表级锁模式、`FreeDisk` 页分配、`LOG` 写前日志、`bTreeLeafPage` 8 KB 固定大小、`Cache` LRU 缓存。

### 23.6 复杂度表

| 操作 | 时间复杂度 | 备注 |
|------|-----------|------|
| `commit()` 版本自增 | O(1) | 单 `++currentVersion` |
| `dropUnusedChunks()` | O(D × R) | D = deadChunks 数，R = chunk 含页面数（位图/缓存清理） |
| `canOverwriteChunk()` | O(1) | 单 chunk 元数据比较 |
| `compact()` | O(C × P) | C = 候选 chunk 数，P = 平均页面大小 |
| `findOldChunks()` 优先级排序 | O(C log C) | 优先级堆插入 |
| `rewriteChunks()` | O(R × P) | R = 待重写页面数，P = 单页序列化大小 |
| `discoverChunk()` 启动扫描 | O(N × B) | N = 总 chunk 数，B = 单 chunk 块数 |
| `isKnownVersion(version)` | O(R + V) | R = 该版本根页引用的 chunk 数，V = layout map 遍历 |

### 23.7 本项目对应

本项目 `engineering/src/db/storage/access/heap/heapam.c` 当前实现无 MVCC 与无版本管理，`dropUnusedChunks` 类机制由 OS 文件系统回收；可借鉴 MVStore 的「45 秒陈化时间窗」设计来支持运行时一致性快照（无需 fsync）。`fillRate * 1000 / age` 压缩优先级公式与 `Chunk.canOverwriteChunk` 的「未被任何活跃版本引用」判定可直接迁移为本项目 B-Tree 的页面回收策略参考。PageStore（legacy）作为「单进程表锁数据库」的实现模板，对本项目 `engineering/src/db/` 的入门级存储引擎教学价值很高。
